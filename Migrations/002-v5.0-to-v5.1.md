## Migrating from Atom 5.0 to Atom 5.1

Atom 5.1 changes one important behavior:

1. **Atom no longer inherits a response cache. Nothing is cached unless you provide a cache and opt an endpoint in.**

Atom 5.1 also adds `resume(decoding:)` and `DecodedResponse`. Those are additive and do not change existing behavior.

There are no breaking public API changes. Existing `Requestable` conformers, `ServiceConfiguration` call sites, and existing `enqueue` / `resume` overloads still compile.

### What happened before

Atom did not explicitly set the session's `urlCache`, so caching depended on the `SessionConfiguration` being used:

| `SessionConfiguration` | Cache behavior |
| --- | --- |
| `.ephemeral`, the default | Private `URLCache` with 512,000 bytes of memory |
| `.default` | `URLCache.shared`, shared with the rest of the host app |
| `.background` | No cache |

That means every package using Atom was potentially caching responses, even though the package never explicitly asked for it.

### What happens now

`ServiceConfiguration` now accepts a cache, and the default is `nil`:

```swift
public init(
    authenticationMethod: AuthenticationMethod = .none,
    cache: URLCache? = nil,
    configuration: SessionConfiguration = .ephemeral,
    // ...
)
```

Atom assigns that value directly to the session.

If `cache` is `nil`, caching is off. That is true for every session configuration, even if the response includes something like:

```http
Cache-Control: public, max-age=600
```

`Requestable` also gets a second switch, which defaults to disabled:

```swift
public var caching: ResponseCaching { .disabled }
```

A request using `.disabled` will never be served from the cache, regardless of the service headers.

So both things need to be enabled before Atom will serve a cached response:

1. The app provides a `URLCache`.
2. The endpoint opts into caching.

### If you do nothing

The app stops reading responses from a cache and makes a network request where it may have previously received a cached response.

For most consumers, that is probably the right behavior and requires no migration work.

The old behavior was implicit, undocumented, and inconsistent. It depended on the session configuration and even on response size, since larger responses may not have been stored by `URLCache` in the first place.

The new default means more network calls, but it also means Atom will not unexpectedly serve stale data.

That is the safer direction to default.

Atom is version-pinned across the portfolio, so nobody picks this change up until they intentionally bump to 5.1.

### If you want caching

In most cases, I would not try to recreate the old behavior exactly... especially for authenticated guest data.

`URLCache` does not vary cached responses based on the `Authorization` header. Two signed-in guests requesting the same URL can potentially interact with the same cached entry.

Also, adding a cache to `ServiceConfiguration` is not enough by itself. Endpoints still default to `.disabled`.

For behavior similar to the old `.ephemeral` setup:

```swift
let responseCache = URLCache(
    memoryCapacity: 512_000,
    diskCapacity: 0,
    directory: nil
)

let configuration = ServiceConfiguration(cache: responseCache)
```

For behavior similar to the old `.default` setup:

```swift
let configuration = ServiceConfiguration(
    cache: .shared,
    configuration: .default
)
```

Then opt endpoints in individually, after confirming the service's freshness behavior:

```swift
var caching: ResponseCaching { .whileCacheFresh }
```

If you provide a cache but opt no endpoints in, Atom can still store responses in that cache... it just will not serve them from it.

### Sign out

If the app provides a cache, the app also owns clearing it.

Atom only holds a reference to the cache. It does not know when a guest signs out and will not clear it automatically.

```swift
responseCache.removeAllCachedResponses()
```

For authenticated services, use a memory-only cache:

```swift
diskCapacity: 0
```

One important detail: opting an endpoint out prevents Atom from serving that response from cache, but it does not necessarily prevent `URLCache` from storing the response.

That means a disk-backed cache can still retain authenticated responses from endpoints that were never opted into cached reads.

See the [Response caching](../README.md#response-caching) section in the README for the full behavior and guidance on which caching mode to use.

### `resume(decoding:)` and `DecodedResponse`

These are additive and separate from the caching change. They just ship in the same release.

```swift
let decoded = try await atom
    .enqueue(Endpoint.refresh)
    .resume(decoding: Seatmap.self)

let seatmap = decoded.model
let servedAt = decoded.response.httpResponse?
    .value(forHTTPHeaderField: "Date")
```

Use `resume(decoding:)` when the caller needs both the decoded model and access to the response... for example, to read headers like `Date` or `ETag`.

`resume(expecting:)` is unchanged. It now goes through the same decode path, so both APIs use the service-configured decoder and both throw `AtomError.decoder(_)` if decoding fails.

### Migration checklist

- [ ] Decide whether the app needs response caching at all. Doing nothing is a valid answer.
- [ ] If it does, create a `URLCache` owned by the app and pass it through `cache:`.
- [ ] Use `diskCapacity: 0` for authenticated services.
- [ ] Opt endpoints in individually, after validating the service's freshness headers.
- [ ] Clear the cache on sign out with `removeAllCachedResponses()`.
- [ ] Clear any app-owned persistent store at the same point if needed.
- [ ] If the app enforces its own maximum age for displayed data, do not use `.whileCacheFresh`.
